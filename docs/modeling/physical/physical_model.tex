	% ============================================================
	\section{Introdução}
	% ============================================================
	
	Este documento apresenta a modelagem física do projeto
	\textit{\projeto}, transformando o modelo lógico aprovado em uma
	estrutura implementável e reproduzível no PostgreSQL.
	
	A modelagem física define:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item o sistema gerenciador de banco de dados;
		\item a organização do banco em camadas;
		\item os tipos de dados físicos;
		\item nulabilidade e valores gerados;
		\item chaves primárias e estrangeiras;
		\item restrições de domínio;
		\item regras de integridade;
		\item índices iniciais;
		\item scripts de criação e remoção;
		\item procedimentos de validação da arquitetura.
	\end{itemize}
	
	A solução utiliza uma arquitetura ELT organizada em três camadas:
	
	\begin{center}
		\textbf{
			Dataset Olist
			$\rightarrow$
			RAW
			$\rightarrow$
			CORE
			$\rightarrow$
			ANALYTICS
			$\rightarrow$
			Power BI / SQL
		}
	\end{center}
	
	A camada RAW preserva os dados recebidos, enquanto o CORE materializa
	o modelo relacional validado. A camada ANALYTICS será construída
	posteriormente a partir do CORE para atender necessidades específicas
	de análise e consumo.
	
	As decisões são documentadas por sua finalidade técnica e semântica,
	sem depender de identificadores internos utilizados no gerenciamento
	do projeto.
	
	% ============================================================
	\section{Sistema Gerenciador de Banco de Dados}
	% ============================================================
	
	O sistema gerenciador de banco de dados adotado é o
	\textbf{PostgreSQL 18}, utilizando sempre a revisão secundária mais
	recente disponível dentro dessa versão principal.
	
	A escolha considera os seguintes critérios:
	
	\begin{itemize}[leftmargin=1.2cm]
		
		\item \textbf{Modelo relacional:}
		suporte maduro a tabelas, relacionamentos, chaves primárias,
		chaves estrangeiras e restrições;
		
		\item \textbf{Integridade dos dados:}
		suporte nativo a \texttt{PRIMARY KEY}, \texttt{FOREIGN KEY},
		\texttt{UNIQUE}, \texttt{CHECK}, nulabilidade e transações;
		
		\item \textbf{Tipos físicos:}
		disponibilidade de tipos adequados para valores monetários,
		coordenadas geográficas, números inteiros e dados temporais;
		
		\item \textbf{Consultas analíticas:}
		suporte a junções, agregações, CTEs, funções de janela e demais
		recursos SQL necessários às análises;
		
		\item \textbf{Automação:}
		possibilidade de executar scripts SQL por linha de comando,
		permitindo validações reproduzíveis;
		
		\item \textbf{Ecossistema:}
		integração com Python, DBeaver, Power BI e outras ferramentas
		de análise;
		
		\item \textbf{Portabilidade e custo:}
		software livre, amplamente utilizado e sem dependência de
		licenciamento proprietário.
		
	\end{itemize}
	
	% ------------------------------------------------------------
	\subsection{Política de versão}
	% ------------------------------------------------------------
	
	O projeto fixa a versão principal \textbf{PostgreSQL 18}, mas não uma
	revisão secundária específica.
	
	Correções e atualizações compatíveis dentro da mesma versão principal
	podem ser utilizadas sem alteração do modelo físico, desde que não
	introduzam incompatibilidades com os scripts SQL versionados.
	
	Segundo a política oficial de versões do PostgreSQL, versões principais
	recebem manutenção por aproximadamente cinco anos. O PostgreSQL 18
	possui suporte previsto até novembro de 2030.
	
	Uma futura migração para outra versão principal deverá ser precedida
	pela execução completa dos scripts de criação e validação.
	
	% ------------------------------------------------------------
	\subsection{Uso do DBeaver}
	% ------------------------------------------------------------
	
	O DBeaver é utilizado como cliente gráfico para interação com o
	PostgreSQL.
	
	Suas funções no projeto incluem:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item criação e gerenciamento da conexão com o servidor;
		\item execução manual dos scripts SQL versionados;
		\item inspeção de schemas, tabelas, colunas e restrições;
		\item visualização de índices e relacionamentos;
		\item execução de consultas exploratórias;
		\item apoio à inspeção dos dados após a carga.
	\end{itemize}
	
	O DBeaver não substitui o PostgreSQL e não constitui a definição
	oficial da estrutura física.
	
	A estrutura reproduzível do banco permanece representada pelos scripts
	SQL versionados.
	
	Credenciais, senhas, portas locais e configurações particulares de
	conexão não fazem parte do repositório.
	
	% ============================================================
	\section{Arquitetura Física em Camadas}
	% ============================================================
	
	A arquitetura foi organizada em três schemas:
	
	\begin{center}
		\texttt{raw}
		$\rightarrow$
		\texttt{core}
		$\rightarrow$
		\texttt{analytics}
	\end{center}
	
	Cada camada possui uma responsabilidade distinta.
	
	% ------------------------------------------------------------
	\subsection{RAW}
	% ------------------------------------------------------------
	
	O schema \texttt{raw} recebe uma representação fiel dos nove arquivos
	CSV utilizados pelo projeto.
	
	Existe uma tabela RAW correspondente a cada arquivo.
	
	Os nomes originais das colunas são mantidos e seus valores são
	armazenados inicialmente como \texttt{text}.
	
	Essa decisão evita que erros de conversão impeçam a ingestão do
	arquivo ou eliminem a representação do valor originalmente recebido.
	
	Cada tabela RAW adiciona somente três campos técnicos:
	
	\begin{itemize}[leftmargin=1.2cm]
		
		\item \texttt{\_id\_raw}:
		identificador técnico da ocorrência carregada;
		
		\item \texttt{\_arquivo\_origem}:
		identificação do arquivo que originou o registro;
		
		\item \texttt{\_carregado\_em}:
		instante em que o registro foi incorporado à camada RAW.
		
	\end{itemize}
	
	Os atributos oriundos do dataset permanecem anuláveis e não recebem
	restrições de negócio.
	
	A chave técnica da RAW identifica a ocorrência armazenada no banco,
	mas não afirma unicidade sobre os dados da fonte.
	
	Valores inconsistentes continuam registráveis nessa camada para que
	possam ser posteriormente identificados, analisados e tratados.
	
	% ------------------------------------------------------------
	\subsection{CORE}
	% ------------------------------------------------------------
	
	O schema \texttt{core} materializa o modelo relacional aprovado.
	
	Ele contém nove tabelas:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item \texttt{cliente};
		\item \texttt{pedido};
		\item \texttt{item\_pedido};
		\item \texttt{produto};
		\item \texttt{vendedor};
		\item \texttt{pagamento};
		\item \texttt{avaliacao};
		\item \texttt{prefixo\_cep};
		\item \texttt{geolocalizacao}.
	\end{itemize}
	
	No fluxo entre RAW e CORE são realizadas:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item conversões de tipos;
		\item renomeações de atributos;
		\item verificações de domínio;
		\item validações de nulabilidade;
		\item deduplicações necessárias;
		\item aplicação de chaves;
		\item aplicação de integridade referencial.
	\end{itemize}
	
	O CORE constitui a fonte relacional íntegra para consultas e para a
	construção posterior das estruturas analíticas.
	
	% ------------------------------------------------------------
	\subsection{ANALYTICS}
	% ------------------------------------------------------------
	
	O schema \texttt{analytics} é criado inicialmente sem tabelas ou views.
	
	Objetos analíticos somente deverão ser adicionados quando estiverem
	definidos:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item a granularidade da estrutura;
		\item a métrica ou necessidade analítica atendida;
		\item as regras de transformação;
		\item a frequência de atualização;
		\item a forma de consumo.
	\end{itemize}
	
	Essa camada poderá conter views, tabelas derivadas, marts ou outras
	estruturas destinadas ao consumo analítico.
	
	Ferramentas como Power BI e consumidores SQL deverão utilizar
	preferencialmente a camada ANALYTICS quando existir uma estrutura
	apropriada para a análise desejada.
	
	% ------------------------------------------------------------
	\subsection{Fluxo físico dos dados}
	% ------------------------------------------------------------
	
	O fluxo previsto é:
	
	\begin{enumerate}[leftmargin=1.2cm]
		\item leitura dos arquivos CSV;
		\item carregamento dos registros na camada RAW;
		\item transformação e validação dos dados;
		\item carga das entidades relacionais no CORE;
		\item geração posterior de estruturas derivadas no ANALYTICS.
	\end{enumerate}
	
	A arquitetura caracteriza um processo ELT porque os dados são
	primeiramente carregados no banco em sua representação bruta e somente
	depois transformados dentro do ambiente de dados.

	% ------------------------------------------------------------
	\subsection{Decisões específicas de representação}
	% ------------------------------------------------------------
	
	Os identificadores do dataset possuem 32 caracteres hexadecimais, mas
	não são armazenados como \texttt{uuid}. A representação física
	preserva a característica observada na fonte e evita impor uma
	semântica técnica que o dataset não declara.
	
	Os prefixos de CEP são atributos textuais com cinco posições.
	Consequentemente, zeros à esquerda possuem significado estrutural e
	não devem ser removidos.
	
	Caso alguma etapa intermediária interprete o CEP como valor numérico,
	sua conversão para o CORE deverá restaurar as cinco posições antes da
	validação.
	
	Não são impostos valores padrão artificiais para atributos ausentes.
	
	As ausências observadas no dataset permanecem representadas por
	\texttt{NULL} quando semanticamente aceitas pelo modelo.

	\section{Política de Integridade Referencial}
	% ============================================================
	
	As relações implementadas no CORE são:
	
	\begin{itemize}[leftmargin=1.2cm]
		
		\item \texttt{pedido.id\_cliente}
		$\rightarrow$
		\texttt{cliente.id\_cliente};
		
		\item \texttt{item\_pedido.id\_pedido}
		$\rightarrow$
		\texttt{pedido.id\_pedido};
		
		\item \texttt{item\_pedido.id\_produto}
		$\rightarrow$
		\texttt{produto.id\_produto};
		
		\item \texttt{item\_pedido.id\_vendedor}
		$\rightarrow$
		\texttt{vendedor.id\_vendedor};
		
		\item \texttt{pagamento.id\_pedido}
		$\rightarrow$
		\texttt{pedido.id\_pedido};
		
		\item \texttt{avaliacao.id\_pedido}
		$\rightarrow$
		\texttt{pedido.id\_pedido};
		
		\item \texttt{cliente.prefixo\_cep}
		$\rightarrow$
		\texttt{prefixo\_cep.prefixo\_cep};
		
		\item \texttt{vendedor.prefixo\_cep}
		$\rightarrow$
		\texttt{prefixo\_cep.prefixo\_cep};
		
		\item \texttt{geolocalizacao.prefixo\_cep}
		$\rightarrow$
		\texttt{prefixo\_cep.prefixo\_cep}.
		
	\end{itemize}
	
	Todas as exclusões referenciadas utilizam:
	
	\begin{center}
		\texttt{ON DELETE RESTRICT}
	\end{center}
	
	As atualizações dos identificadores referenciados utilizam:
	
	\begin{center}
		\texttt{ON UPDATE NO ACTION}
	\end{center}
	
	Não são utilizadas exclusões em cascata.
	
	A remoção automática de registros relacionados poderia eliminar
	informações históricas de outras entidades sem uma decisão explícita
	do processo de dados.
	
	% ============================================================
	\section{Estratégia Inicial de Índices}
	% ============================================================
	
	A estratégia de indexação foi definida de forma conservadora.
	
	Índices somente são adicionados quando derivados diretamente de
	restrições estruturais ou de relacionamentos cuja navegação possui
	utilidade clara.
	
	O PostgreSQL cria automaticamente índices B-tree para:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item chaves primárias;
		\item restrições \texttt{UNIQUE}.
	\end{itemize}
	
	Entretanto, o PostgreSQL não cria automaticamente índices para as
	colunas que apenas participam como lado referenciante de uma chave
	estrangeira.
	
	Uma chave estrangeira é considerada coberta quando suas colunas
	ocupam o prefixo à esquerda de algum índice existente.

		\item
		\texttt{idx\_cliente\_prefixo\_cep}
		sobre \texttt{cliente(prefixo\_cep)};
		
		\item
		\texttt{idx\_vendedor\_prefixo\_cep}
		sobre \texttt{vendedor(prefixo\_cep)};
		
		\item
		\texttt{idx\_item\_pedido\_id\_produto}
		sobre \texttt{item\_pedido(id\_produto)};
		
		\item
		\texttt{idx\_item\_pedido\_id\_vendedor}
		sobre \texttt{item\_pedido(id\_vendedor)};
		
		\item
		\texttt{idx\_avaliacao\_id\_pedido}
		sobre \texttt{avaliacao(id\_pedido)};
		
		\item
		\texttt{idx\_geolocalizacao\_prefixo\_cep}
		sobre \texttt{geolocalizacao(prefixo\_cep)}.
		
	\end{itemize}
	
	Esses índices correspondem às chaves estrangeiras que não estão
	adequadamente cobertas pelo prefixo de uma chave primária ou
	restrição UNIQUE existente.
	
	% ------------------------------------------------------------
	\subsection{RAW}
	% ------------------------------------------------------------
	
	Nenhum índice secundário adicional é inicialmente criado na camada RAW.
	
	O objetivo dessa camada é priorizar simplicidade e desempenho de
	ingestão.
	
	Adicionar índices antes da existência de padrões reais de consulta
	aumentaria o custo de escrita sem benefício comprovado.
	
	Cada tabela possui apenas o índice decorrente de sua chave primária
	técnica.
	
	% ------------------------------------------------------------
	\subsection{ANALYTICS}
	% ------------------------------------------------------------
	
	Nenhum índice é criado inicialmente no schema ANALYTICS porque ele
	ainda não contém objetos analíticos.
	
	A estratégia deverá ser definida individualmente para cada estrutura
	que venha a ser criada.
	
	% ------------------------------------------------------------
	\subsection{Revisão posterior}
	% ------------------------------------------------------------
	
	Os índices iniciais não são considerados definitivos.
	
	Após a carga e o início das consultas deverão ser avaliados:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item estatísticas do PostgreSQL;
		\item consultas recorrentes;
		\item seletividade;
		\item custo de manutenção;
		\item planos obtidos com \texttt{EXPLAIN};
		\item planos obtidos com \texttt{EXPLAIN ANALYZE}.
	\end{itemize}
	
	Índices adicionais somente deverão ser criados com evidência de uso.
	
	% ============================================================
	\section{Scripts da Arquitetura Física}
	% ============================================================
	
	A implementação é representada por scripts SQL versionados.
	
	Os principais artefatos são:
	
	\begin{itemize}[leftmargin=1.2cm]
		
		\item \texttt{create\_schema.sql}
		
		Cria os schemas RAW, CORE e ANALYTICS, bem como suas respectivas
		tabelas e restrições;
		
		\item \texttt{create\_indexes.sql}
		
		Cria os seis índices secundários adicionais definidos para o CORE;
		
		\item \texttt{validate\_schema.sql}
		
		Valida propriedades estruturais do catálogo e o comportamento das
		principais restrições;
		
		\item \texttt{drop\_indexes.sql}
		
		Remove explicitamente os índices secundários adicionais;
		
		\item \texttt{drop\_schema.sql}
		
		Remove as estruturas físicas em ordem segura.
		
	\end{itemize}
	
	% ------------------------------------------------------------
	\subsection{Execução pelo DBeaver}
	% ------------------------------------------------------------
	
	Para criar e validar a arquitetura em uma instância limpa:
	
	\begin{enumerate}[leftmargin=1.2cm]
		
		\item conectar-se ao servidor PostgreSQL;
		
		\item abrir um editor SQL associado ao banco desejado;
		
		\item executar \texttt{create\_schema.sql};
		
		\item confirmar a criação dos schemas e tabelas;
		
		\item executar \texttt{create\_indexes.sql};
		
		\item executar \texttt{validate\_schema.sql};
		
		\item verificar se a validação foi concluída sem falhas.
		
	\end{enumerate}
	
	A criação da estrutura não utiliza redefinição silenciosa de objetos.
	
	Se os schemas já existirem, uma nova execução do script de criação
	deverá falhar em vez de substituir estruturas existentes.
	
	Essa decisão reduz o risco de alterações involuntárias em um banco já
	criado.
	
	% ------------------------------------------------------------
	\subsection{Remoção}
	% ------------------------------------------------------------
	
	Os scripts de remoção devem ser utilizados somente:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item em ambientes descartáveis;
		\item em testes automatizados;
		\item quando houver decisão explícita de reconstruir o banco.
	\end{itemize}
	
	Uma sequência possível é:
	
	\begin{enumerate}[leftmargin=1.2cm]
		\item executar \texttt{drop\_indexes.sql};
		\item executar \texttt{drop\_schema.sql}.
	\end{enumerate}
	
	A operação de remoção foi projetada para poder ser repetida sem deixar
	o ambiente em estado intermediário inconsistente.

	% ------------------------------------------------------------
	\subsection{Teste da camada RAW}
	% ------------------------------------------------------------
	
	A RAW foi testada com valores que seriam inválidos segundo as regras
	do CORE.
	
	A inserção foi aceita conforme esperado.
	
	Isso confirma que a camada não está aplicando antecipadamente regras
	de negócio sobre os valores recebidos.
	
	Sua função permanece sendo a preservação da evidência original da
	fonte.
	
	% ------------------------------------------------------------
	\subsection{Teste da camada CORE}
	% ------------------------------------------------------------
	
	O CORE foi submetido a inserções deliberadamente inválidas.
	
	Foram testados, entre outros comportamentos:
	
	\begin{itemize}[leftmargin=1.2cm]
		
		\item prefixo de CEP incompatível com o domínio;
		
		\item tentativa de duplicação de chave primária;
		
		\item tentativa de criação de referência órfã.
		
	\end{itemize}
	
	As operações foram rejeitadas conforme esperado.
	
	Isso confirma que as regras de integridade estão efetivamente sendo
	aplicadas pelo PostgreSQL e não apenas documentadas.
	
	% ------------------------------------------------------------
	\subsection{Isolamento dos testes}
	% ------------------------------------------------------------
	
	Os registros utilizados para testar as restrições foram executados
	dentro de transações e posteriormente revertidos.
	
	Dessa forma, a execução da validação não deixa registros fictícios
	incorporados ao banco.
	
	% ------------------------------------------------------------
	\subsection{Repetibilidade da criação}
	% ------------------------------------------------------------
	
	Após uma primeira criação bem-sucedida, o script de criação foi
	executado novamente.
	
	A segunda tentativa foi rejeitada intencionalmente porque os schemas
	já existiam.
	
	As dezoito tabelas previamente criadas permaneceram intactas.
	
	Esse comportamento protege o ambiente contra redefinições silenciosas.
	
	% ------------------------------------------------------------
	\subsection{Repetibilidade da remoção}
	% ------------------------------------------------------------
	
	A rotina de remoção foi executada mais de uma vez.
	
	Após a primeira remoção, uma nova execução não produziu falha
	decorrente da inexistência dos objetos.
	
	Esse comportamento permite reconstruir ambientes descartáveis de
	forma previsível.

	\section{Responsabilidades da Carga e Transformação}
	% ============================================================
	
	A modelagem física define as estruturas que deverão receber os dados,
	mas não antecipa todas as regras operacionais do processo de carga.
	
	O processo subsequente deverá:
	
	\begin{itemize}[leftmargin=1.2cm]
		
		\item extrair os nove arquivos CSV;
		
		\item carregar os registros na RAW com rastreabilidade;
		
		\item converter tipos físicos;
		
		\item normalizar prefixos de CEP;
		
		\item validar domínios;
		
		\item tratar duplicidades quando necessário;
		
		\item construir as entidades do CORE;
		
		\item respeitar a ordem necessária para as chaves estrangeiras;
		
		\item contabilizar registros recebidos, carregados, transformados e
		rejeitados;
		
		\item reconciliar os volumes entre fonte, RAW e CORE.
		
	\end{itemize}
	
	Regras específicas de transformação deverão permanecer separadas das
	restrições puramente estruturais.
	
	Isso evita introduzir no modelo físico interpretações analíticas ou
	correções que ainda não tenham sido justificadas.

	% ============================================================
	\section{Conclusão}
	% ============================================================
	
	A modelagem física transforma o modelo lógico em uma implementação
	relacional reproduzível no PostgreSQL.
	
	A arquitetura separa claramente três responsabilidades:
	
	\begin{itemize}[leftmargin=1.2cm]
		
		\item \textbf{RAW:}
		preservação rastreável dos dados recebidos;
		
		\item \textbf{CORE:}
		representação relacional tipada, validada e íntegra;
		
		\item \textbf{ANALYTICS:}
		estruturas derivadas destinadas ao consumo analítico.
		
	\end{itemize}
	
	O PostgreSQL 18 foi adotado como SGBD, enquanto o DBeaver atua como
	cliente gráfico de apoio à administração e execução dos scripts.
	
	Os tipos físicos foram definidos a partir do perfil observado no
	dataset, preservando identificadores, valores ausentes, prefixos de
	CEP, coordenadas e características temporais da fonte.
	
	A estratégia inicial de índices utiliza os índices implícitos das
	restrições do PostgreSQL e adiciona somente os seis índices necessários
	para complementar a cobertura das chaves estrangeiras.
	
	Os scripts de criação, indexação, validação e remoção permitem
	reproduzir e testar a arquitetura sem depender de configuração manual
	do cliente gráfico.
	
	Os testes realizados confirmaram a estrutura esperada do catálogo,
	a permissividade intencional da RAW, a aplicação efetiva das regras de
	integridade no CORE e a segurança das rotinas de criação e remoção.
	
	Com a arquitetura física validada, o banco encontra-se preparado para
	receber os arquivos do dataset, registrar sua origem na RAW,
	transformar os dados para o CORE e posteriormente disponibilizar
	estruturas analíticas para consultas SQL e ferramentas de Business
	Intelligence.
