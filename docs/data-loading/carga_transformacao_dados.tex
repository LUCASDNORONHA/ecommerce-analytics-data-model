	% ============================================================
	\section{Introdução}
	% ============================================================
	
	Este documento consolida a preparação automatizada do banco de dados, o processo
	de carga, a transformação e a validação dos dados do projeto
	\textit{\projeto}, desde a criação da estrutura física no PostgreSQL até a
	publicação e auditoria das entidades relacionais no schema \texttt{core}.
	
	A preparação da infraestrutura de banco é tratada separadamente do ELT. O
	componente \texttt{database} garante que o banco de destino exista, aplica os
	scripts versionados do modelo físico, cria os índices e valida a arquitetura.
	Somente após essa etapa o pipeline ELT realiza a carga dos nove arquivos CSV do
	\textit{Brazilian E-Commerce Public Dataset by Olist} na RAW e a transformação
	para o CORE.
	
	A validação pós-carga é executada de forma independente pelo componente
	\texttt{validation}. Seu objetivo é confirmar volumes, integridade, qualidade,
	nulabilidade e correspondência entre os valores esperados a partir da RAW e os
	dados efetivamente publicados no CORE.
	
	A solução busca garantir reprodutibilidade, rastreabilidade, integridade,
	atomicidade, reconciliação entre fonte e destino e validação independente do
	resultado publicado.
	
	\begin{center}
		\textbf{
			PostgreSQL
			$\rightarrow$
			database.setup
			$\rightarrow$
			RAW
			$\rightarrow$
			CORE
			$\rightarrow$
			validation
			$\rightarrow$
			ANALYTICS
			$\rightarrow$
			Power BI / SQL
		}
	\end{center}
	
	As decisões são descritas por sua finalidade técnica e semântica, sem depender
	de identificadores internos utilizados no gerenciamento do projeto.
	
	% ============================================================
	\section{Preparação Automatizada do Banco}
	% ============================================================
	
	A criação e a preparação da estrutura física são responsabilidades anteriores
	ao ELT e, por esse motivo, permanecem isoladas no pacote \texttt{database}. Os
	scripts SQL em \texttt{models/physical/} continuam sendo a fonte da verdade para
	o modelo físico; o código Python atua apenas como orquestrador.
	
	\subsection{Identificação do banco de destino}
	
	A conexão é definida pela variável de ambiente \texttt{DATABASE\_URL}. O nome
	do banco é extraído da própria URL e registrado no log antes de qualquer
	alteração estrutural.
	
	No ambiente local, a configuração pode ser mantida em arquivo \texttt{.env},
	ignorado pelo Git:
	
	\begin{verbatim}
		DATABASE_URL=postgresql://usuario:senha@localhost:5432/ecommerce_analytics
	\end{verbatim}
	
	O arquivo \texttt{.env.example} documenta a variável necessária sem expor
	credenciais reais.
	
	\subsection{Criação automática do database}
	
	Antes de aplicar a estrutura física, o processo consulta o catálogo
	\texttt{pg\_database} por meio do banco administrativo \texttt{postgres}. Se o
	database indicado em \texttt{DATABASE\_URL} ainda não existir, ele é criado
	automaticamente.
	
	Essa operação depende de o usuário PostgreSQL possuir permissão para
	\texttt{CREATE DATABASE}. Caso a permissão não esteja disponível, a execução é
	interrompida e o erro é informado sem tentativa de contorno.
	
	A verificação por catálogo evita dependência de mensagens textuais do servidor
	e, portanto, não depende do idioma configurado no PostgreSQL.
	
	\subsection{Aplicação do modelo físico}
	
	Após garantir a existência do database, o processo aplica os artefatos físicos
	versionados nesta ordem:
	
	\begin{enumerate}[leftmargin=1.2cm]
		\item \texttt{models/physical/create\_schema.sql};
		\item \texttt{models/physical/create\_indexes.sql};
		\item \texttt{models/physical/validate\_schema.sql}.
	\end{enumerate}
	
	A validação final confirma a presença dos schemas, tabelas, colunas, identities,
	PKs, FKs, constraints e índices definidos para a arquitetura física.
	
	\subsection{Reconstrução controlada}
	
	Quando o banco já existe, a opção \texttt{--reset} executa
	\texttt{drop\_schema.sql} antes da recriação da estrutura:
	
	\begin{verbatim}
		uv run python -m database.setup --reset
	\end{verbatim}
	
	O \texttt{--reset} não remove o database PostgreSQL. Apenas a estrutura
	pertencente ao projeto é reconstruída. Se o database for criado na própria
	execução, a etapa de remoção é omitida por não existir estrutura anterior a ser
	descartada.
	
	Para um ambiente novo, a preparação pode ser executada simplesmente por:
	
	\begin{verbatim}
		uv run python -m database.setup
	\end{verbatim}
	
	% ============================================================
	\section{Arquitetura do ELT}
	% ============================================================
	
	\subsection{Camada RAW}
	
	A camada RAW preserva os valores recebidos da fonte. Existe uma tabela
	correspondente a cada CSV; as colunas de negócio mantêm os nomes originais e
	são armazenadas inicialmente como \texttt{text}.
	
	Cada ocorrência recebe os metadados técnicos:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item \texttt{\_id\_raw}: identificador técnico da ocorrência carregada;
		\item \texttt{\_arquivo\_origem}: identificação do arquivo de origem;
		\item \texttt{\_carregado\_em}: instante em que o registro foi incorporado à RAW.
	\end{itemize}
	
	A política de recarga é substitutiva e atômica: uma nova carga aprovada
	substitui integralmente a anterior. Falhas durante a operação provocam
	\textit{rollback}, preservando o estado previamente publicado.
	
	\subsection{Camada CORE}
	
	O CORE materializa o modelo relacional aprovado. As transformações incluem:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item conversões explícitas de tipos;
		\item renomeações de atributos;
		\item aplicação das constraints físicas;
		\item derivação de prefixos de CEP;
		\item consolidação das duplicidades integrais de geolocalização;
		\item reconciliação dos volumes inseridos.
	\end{itemize}
	
	A ordem de dependências adotada é:
	
	\begin{enumerate}[leftmargin=1.2cm]
		\item \texttt{core.prefixo\_cep};
		\item \texttt{core.cliente}, \texttt{core.produto} e \texttt{core.vendedor};
		\item \texttt{core.pedido} e \texttt{core.geolocalizacao};
		\item \texttt{core.item\_pedido}, \texttt{core.pagamento} e \texttt{core.avaliacao}.
	\end{enumerate}
	
	\subsection{Atomicidade do pipeline completo}
	
	O comando completo usa uma única conexão PostgreSQL para o fluxo CSV
	$\rightarrow$ RAW $\rightarrow$ CORE. O controle transacional é realizado pelo
	\texttt{psycopg}. Se qualquer arquivo, conversão, constraint ou reconciliação
	falhar, RAW e CORE retornam conjuntamente ao estado anterior.

	\section{Regras de Qualidade e Validação}
	% ============================================================
	
	A validação pós-carga é executada de forma independente do pipeline responsável
	pela transformação. Essa separação reduz o risco de uma implementação validar
	a si própria utilizando exatamente a mesma lógica que produziu o resultado.
	
	O processo está organizado em quatro grupos de controles:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item \textbf{reconciliação}: comparação entre volumes esperados na RAW e
		volumes publicados no CORE;
		\item \textbf{integridade}: validação de unicidade, chaves primárias,
		\texttt{UNIQUE} e integridade referencial;
		\item \textbf{qualidade}: validação de nulabilidade, formatos, domínios,
		limites geográficos e valores numéricos;
		\item \textbf{transformação}: comparação do conteúdo da RAW com o conteúdo
		efetivamente publicado no CORE após as conversões previstas.
	\end{itemize}
	
	A execução validada contempla \textbf{87 regras automáticas}, distribuídas da
	seguinte forma:
	
	{\small
		\renewcommand{\arraystretch}{1.2}
		\begin{longtable}{
				|>{\raggedright\arraybackslash}p{7.5cm}|
				>{\raggedleft\arraybackslash}p{3.0cm}|
				>{\raggedright\arraybackslash}p{4.3cm}|
			}
			\hline
			\rowcolor{AzulCorporativo}
			\textcolor{white}{\textbf{Categoria}} &
			\textcolor{white}{\textbf{Regras}} &

			\rowcolor{AzulCorporativo}

			\textcolor{white}{\textbf{Resultado}} \\\hline

			Reconciliação RAW $\rightarrow$ CORE & 9 & Aprovadas \\\hline
			Integridade estrutural e referencial & 19 & Aprovadas \\\hline
			Validação dinâmica de \texttt{NOT NULL} & 39 & Aprovadas \\\hline
			Domínios e qualidade dos valores & 11 & Aprovadas \\\hline
			Correspondência das transformações & 9 & Aprovadas \\\hline
			\textbf{Total} & \textbf{87} & \textbf{87 aprovadas} \\\hline
		\end{longtable}
	}
	
	Entre os controles aplicados estão:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item ausência de duplicidades nas chaves primárias;
		\item unicidade de \texttt{pedido.id\_cliente};
		\item inexistência de registros órfãos nas nove relações de chave estrangeira;
		\item validação dinâmica de todas as 39 colunas \texttt{NOT NULL} existentes
		no CORE;
		\item validação dos formatos dos identificadores;
		\item prefixos de CEP com cinco dígitos e preservação de zeros à esquerda;
		\item validação dos domínios de UF, status de pedido e tipo de pagamento;
		\item valores monetários não negativos;
		\item sequenciais e quantidades compatíveis com seus domínios;
		\item notas de avaliação entre 1 e 5;
		\item dimensões físicas não negativas;
		\item latitude e longitude dentro dos limites geográficos válidos;
		\item ausência de cidades obrigatórias vazias;
		\item correspondência integral entre os valores transformados da RAW e os
		valores armazenados no CORE.
	\end{itemize}
	
	As verificações de transformação não se limitam à quantidade de registros.
	Para cada uma das nove entidades do CORE, o conjunto esperado é reconstruído a
	partir da RAW utilizando as conversões definidas no processo de carga e
	comparado ao conjunto efetivamente persistido.
	
	Assim, uma tabela com o volume correto, mas contendo valores diferentes dos
	esperados, também reprova a validação.
	
	A geolocalização constitui uma transformação deliberadamente não bijetiva.
	As 1.000.163 ocorrências preservadas na RAW resultam em 738.332 ocorrências
	distintas no CORE, correspondendo à consolidação de
	\textbf{261.831 duplicidades integrais}. A deduplicação considera conjuntamente
	prefixo de CEP, latitude, longitude, cidade e estado.
	
	A entidade \texttt{prefixo\_cep} é derivada da união dos prefixos presentes em
	clientes, vendedores e geolocalização, resultando em
	\textbf{19.177 prefixos distintos}.
	
	O arquivo \texttt{product\_category\_name\_translation.csv} permanece preservado
	na RAW, porém não participa da transformação atualmente aprovada para o CORE.
	O atributo \texttt{produto.nome\_categoria} mantém o valor original
	\texttt{product\_category\_name}. Dessa forma, a ausência de uma tabela CORE
	correspondente ao arquivo de tradução não caracteriza perda acidental de dados.

	% ============================================================
	\section{Configuração e Execução}
	% ============================================================
	
	Credenciais não são versionadas. No ambiente local, a conexão pode ser
	armazenada em \texttt{.env}, ignorado pelo Git, enquanto
	\texttt{.env.example} documenta a variável necessária sem conter segredos.
	
	\begin{verbatim}
		DATABASE_URL=postgresql://usuario:senha@localhost:5432/ecommerce_analytics
	\end{verbatim}
	
	A preparação inicial do banco é executada com:
	
	\begin{verbatim}
		uv run python -m database.setup
	\end{verbatim}
	
	Se o database ainda não existir, ele é criado automaticamente antes da
	aplicação do modelo físico.
	
	Para reconstruir a estrutura pertencente ao projeto em um database já
	existente:
	
	\begin{verbatim}
		uv run python -m database.setup --reset
	\end{verbatim}
	
	Após a preparação física, a execução operacional do pipeline completo é:
	
	\begin{verbatim}
		uv run python -m elt.pipeline
	\end{verbatim}
	
	A validação independente do resultado publicado é executada por:
	
	\begin{verbatim}
		uv run python -m validation.elt_validation
	\end{verbatim}
	
	O fluxo completo e reproduzível é, portanto:
	
	\begin{verbatim}
		uv run python -m database.setup --reset
		uv run python -m elt.pipeline
		uv run python -m validation.elt_validation
	\end{verbatim}
	
	A pré-validação das fontes sem conexão com o PostgreSQL continua disponível
	por:
	
	\begin{verbatim}
		uv run python -m elt.pipeline --validate-only
	\end{verbatim}
	
	Cada execução completa do ELT gera um log JSON local em:
	
	\begin{verbatim}
		outputs/data-loading/logs/full_load_<run_id>.json
	\end{verbatim}
	
	O registro contém perfis e hashes das fontes, reconciliações RAW e CORE, hash
	do SQL de transformação, horários, modo de execução, status e erro quando
	houver. A URL de conexão não é registrada.
	
	A validação pós-carga gera separadamente:
	
	\begin{verbatim}
		outputs/data-loading/validation/elt_validation_<run_id>.json
	\end{verbatim}
	
	Esse relatório registra o identificador da execução, database avaliado,
	horários, status geral, resumo das regras e resultado individual de cada
	controle.

	\section{Validação e Testes}
	% ============================================================
	
	A implementação foi submetida a validações automatizadas e testes de
	integração sobre banco PostgreSQL real.
	
	Durante o desenvolvimento, o ELT foi validado em uma instância PostgreSQL 18.6
	temporária e isolada. Duas execuções completas consecutivas demonstraram que a
	política de recarga não produz acumulação de registros. Uma falha deliberada ao
	final da transformação confirmou ainda que RAW e CORE participam da mesma
	unidade transacional e retornam conjuntamente ao estado anterior em caso de
	erro.
	
	A automação de preparação do banco também foi validada em dois cenários:
	utilização de um database previamente existente e criação automática de um
	database inexistente. No segundo caso, o processo identificou a ausência pelo
	catálogo \texttt{pg\_database}, criou o database, aplicou a estrutura física,
	criou os índices e concluiu sua validação.
	
	A suíte específica de \texttt{database.setup} possui oito testes automatizados
	que cobrem:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item extração do nome do database a partir da URL;
		\item construção da URL administrativa apontando para \texttt{postgres};
		\item não criação quando o database já existe;
		\item criação quando o database não existe;
		\item preparação normal sem remoção da estrutura;
		\item ordem dos scripts no modo \texttt{--reset};
		\item ausência de remoção quando o database acaba de ser criado;
		\item falha controlada quando \texttt{DATABASE\_URL} não está configurada.
	\end{itemize}
	
	A suíte específica de validação possui \textbf{16 testes automatizados},
	incluindo cenários aprovados e reprovados para reconciliação, integridade,
	qualidade, nulabilidade e correspondência das transformações.
	
	A suíte completa do projeto possui, no snapshot documentado,
	\textbf{44 testes automatizados}, todos aprovados.
	
	Ela é executada por:
	
	\begin{verbatim}
		uv run python -m unittest discover -s tests -v
	\end{verbatim}
	
	A validação final sobre a base persistente foi executada por:
	
	\begin{verbatim}
		uv run python -m validation.elt_validation
	\end{verbatim}
	
	O resultado obtido foi:
	
	\begin{center}
		\textbf{\textcolor{AzulCorporativo}{
				APPROVED --- 87 de 87 regras aprovadas
		}}
	\end{center}
	
	A execução completa da auditoria levou aproximadamente
	\textbf{8,5 segundos} no ambiente utilizado.
	
	As nove verificações de correspondência RAW $\rightarrow$ CORE apresentaram
	zero divergências em:
	
	\begin{itemize}[leftmargin=1.2cm]
		\item \texttt{prefixo\_cep};
		\item \texttt{cliente};
		\item \texttt{produto};
		\item \texttt{vendedor};
		\item \texttt{pedido};
		\item \texttt{item\_pedido};
		\item \texttt{pagamento};
		\item \texttt{avaliacao};
		\item \texttt{geolocalizacao}.
	\end{itemize}
	
	Portanto, além da igualdade dos volumes esperados, foi comprovado que os
	conteúdos publicados correspondem aos conjuntos derivados da RAW pelas
	transformações implementadas.

	\subsection{Resultado da validação pós-carga}
	
	A reconciliação final não identificou divergências bloqueantes.
	
	A camada CORE contém \textbf{1.308.197 registros físicos} distribuídos pelas
	nove entidades aprovadas. Esse total não deve ser comparado diretamente aos
	\textbf{1.550.922 registros da RAW} como se as duas camadas compartilhassem a
	mesma granularidade.
	
	A principal redução ocorre em geolocalização:
	
	\begin{center}
		1.000.163 ocorrências RAW
		$\rightarrow$
		738.332 ocorrências CORE
	\end{center}
	
	A diferença de \textbf{261.831 ocorrências} corresponde exclusivamente a
	duplicidades integrais consolidadas de forma determinística.
	
	Além disso, \texttt{core.prefixo\_cep} constitui uma entidade derivada com
	19.177 registros, enquanto o arquivo de tradução de categorias, com 71
	registros, permanece exclusivamente na RAW por não possuir destino definido no
	modelo CORE atual.
	
	Todos esses comportamentos foram considerados explicitamente pelas regras de
	reconciliação e transformação e foram aprovados.

	\section{Rastreabilidade e Limites}
	% ============================================================
	
	A RAW mantém os valores originais e metadados técnicos que permitem relacionar
	cada ocorrência ao arquivo e à execução responsável por sua ingestão.
	
	O pipeline registra perfis das fontes, quantidade de registros, hashes SHA-256,
	reconciliações, hash do SQL de transformação, horários e resultado da execução.
	
	A validação pós-carga possui identificação independente e produz relatório JSON
	contendo o resultado individual das regras executadas. Dessa forma, uma
	reprovação pode ser associada à categoria e à regra que detectou a divergência.
	
	A preparação do banco registra explicitamente o database de destino antes das
	operações estruturais. A URL de conexão e suas credenciais não são incluídas
	nos logs.
	
	O modo \texttt{--reset} não remove o database PostgreSQL; apenas a estrutura
	pertencente ao projeto é reconstruída.
	
	Embora a implementação atual identifique quantitativamente a regra violada, o
	registro detalhado de cada ocorrência inválida --- incluindo, quando aplicável,
	arquivo de origem, \texttt{\_id\_raw}, coluna e valor original --- permanece
	como possibilidade de evolução para fontes futuras que efetivamente apresentem
	violações bloqueantes.
	
	No snapshot utilizado nesta entrega nenhuma das 87 regras executáveis
	apresentou violação.
	
	Regras temporais e comportamentais que possam representar características ou
	anomalias legítimas da fonte, como diferenças incomuns entre eventos do ciclo
	do pedido, não foram transformadas automaticamente em critérios bloqueantes.
	Essas características pertencem à análise de qualidade semântica e poderão ser
	exploradas posteriormente sem modificar retrospectivamente os dados originais.
	
	Agendamento, monitoramento operacional contínuo e objetos do schema
	\texttt{analytics} não fazem parte deste documento.
	
	% ============================================================
	\section{Conclusão}
	% ============================================================
	
	O processo de preparação, carga, transformação e validação dos dados está
	implementado de forma reproduzível e verificável.
	
	O componente \texttt{database.setup} garante a existência do database e aplica
	o modelo físico versionado sem transferir essa responsabilidade ao ELT. O
	pipeline realiza a pré-validação das nove fontes contratadas, carrega
	1.550.922 ocorrências na RAW e transforma os dados para as nove entidades do
	CORE dentro de uma única unidade transacional.
	
	O resultado publicado contém 1.308.197 registros no CORE, incluindo 738.332
	ocorrências únicas de geolocalização e 19.177 prefixos de CEP derivados.
	
	A validação pós-carga é realizada por componente independente e verifica
	volumes, integridade, nulabilidade, domínios e correspondência entre as
	transformações esperadas e os dados persistidos.
	
	Na execução de referência, as \textbf{87 regras foram aprovadas sem
		divergências}. A suíte automatizada completa também foi concluída com
	\textbf{44 de 44 testes aprovados}.
	
	Esses resultados demonstram que a camada CORE foi produzida de acordo com o
	modelo físico e com as regras de transformação definidas, sem perda
	silenciosa, acumulação indevida ou quebra conhecida de integridade.
	
	A etapa de carga e transformação fica, portanto, concluída com evidência
	reproduzível e rastreável. O banco encontra-se apto para a construção das
	estruturas do schema \texttt{analytics} e para o desenvolvimento das análises
	destinadas ao consumo por SQL e ferramentas de Business Intelligence.
